# HabitTrack

A habit-tracking backend built as **.NET 10 microservices**, with an **Azure deployment and CI/CD pipeline** on top. Three services, each with its own database, trust each other through JWTs and an internal API key. A timer-triggered Azure Function detects streak milestones.

## Highlights

- Three microservices (User, Habit, Notification), each owning its own SQL database
- Cross-service JWT trust plus an internal API key (`X-Internal-Api-Key`) for service-to-service calls
- AI-generated habit insights via the Anthropic Messages API, with retries, timeout, caching and a graceful fallback
- Custom middleware, all five ASP.NET filter types, EF Core depth (N+1 fix, migrations), DI lifetimes
- xUnit test suite that gates every deployment
- Docker: a Dockerfile per service and one `docker compose up` that starts SQL Server and all three services
- Azure: App Service with a staging slot, Azure SQL, Key Vault + Managed Identity, Azure Functions
- GitHub Actions CI/CD with passwordless OIDC login, smoke test, slot swap and automatic rollback


## Services

| Service | Responsibility |
|---|---|
| **UserService** | Registration, login, JWT issuing, user profiles |
| **HabitService** | Habits, check-ins, streak calculation, at-risk and milestone logic, AI habit insights |
| **NotificationService** | Stores and serves notifications; called by HabitService with the internal API key |
| **MilestoneFunction** | Azure Function (timer trigger) that finds habits crossing a streak milestone |

## What this project deliberately demonstrates

- **Middleware:** custom middleware in the request pipeline
- **Filters:** authorization, resource, action, exception and result filters
  
  | Filter | Used for |
  |---|---|
  | Authorization | Access checks before the action runs |
  | Resource | Short-circuiting / caching around the action |
  | Action | Cross-cutting logic before and after actions |
  | Exception | Consistent error responses |
  | Result | Shaping the response |

- **Auth:** JWT bearer authentication shared across services, plus an API-key scheme for internal calls
- **EF Core:** per-service DbContext, migrations, an N+1 query fixed with eager loading and projection
- **Dependency injection:** correct lifetimes (singleton / scoped / transient)
- **Testing:** xUnit tests for streak and milestone logic, run by CI on every push

## AI habit insights (Anthropic integration)

`GET /api/habits/{id}/insights` (JWT required) returns one short, personalised insight about a habit, generated by the Anthropic Messages API.

```
GET /api/habits/{id}/insights
        |
 HabitInsightsService
   1. load habit, reject with 404 unless it belongs to the caller
   2. check the 12-hour in-memory cache            <- after the ownership check, so a cache hit can never skip authorization
   3. read check-in dates, compute current and longest streak
   4. InsightAggregator builds a HabitInsightSummary
   5. AnthropicInsightsClient builds a prompt and calls POST v1/messages
   6. parse the JSON reply, cache it, return { "insight": "..." }
```

- **Aggregation first:** only a small summary is sent to the model (habit name, frequency, current and longest streak, check-ins and completion rate over the last 30 days, and the weekdays most often missed). Raw check-in history is never sent.
- **Structured output:** the prompt asks for raw JSON `{ "insight": "..." }`. The client strips markdown code fences if the model adds them, then deserializes.
- **Resilience:** 15 second timeout per attempt, up to 3 attempts with exponential backoff on HTTP 429 and on timeouts. Other API errors and parse failures return `null` rather than throwing.
- **Graceful degradation:** if no insight can be produced, the endpoint returns "Insight temporarily unavailable. Check back soon!" instead of an error, so the habit screens never break because of the AI dependency.
- **Cost control:** insights are cached per habit for 12 hours, and `max_tokens` is capped at 300.
- **Typed HTTP client:** configured with `AddHttpClient<IInsightsClient, AnthropicInsightsClient>`, behind an `IInsightsClient` interface so tests can fake it.
- **Configuration:** bound from the `Anthropic` section (`ApiKey`, `BaseUrl`, `Model`, `ApiVersion`, `MaxTokens`). Provide the key as `Anthropic__ApiKey` (environment variable or user secrets); never commit it.

## Azure deployment and CI/CD

### What is deployed

| Component | Azure service | Notes |
|---|---|---|
| UserService | App Service (Linux, .NET 10, S1) | `production` and `staging` slots |
| UserDb, HabitDb | Azure SQL | Free serverless offer and Basic DTU tier |
| Secrets | Key Vault (RBAC mode) | Read by Managed Identity, no secrets in code |
| MilestoneFunction | Azure Functions (Consumption) | Isolated worker, timer trigger |
| Pipeline | GitHub Actions | OIDC login, no stored Azure passwords |

HabitService and NotificationService were not deployed. The resources have since been torn down, so there are no live endpoints.

### Architecture on Azure

```
GitHub push --> GitHub Actions --OIDC--> Azure
                                          |
        +---------------------------------+----------------------+
        v                                                        v
  App Service (UserService)                         Function App (MilestoneFunction)
   [staging] <--swap--> [production]                          |
        |                                                     |
        +--- Managed Identity ---> Key Vault (JwtKey, SQL)    +--> Azure SQL (Habit + User DBs)
        |
        +--> Azure SQL (UserDb)
```

### Configuration and secrets

- `appsettings.json` is git-ignored, so CI and Azure never receive it. Configuration comes from App Settings instead.
- Hierarchical keys use double underscores: `Jwt__Key` maps to `Jwt:Key`.
- Sensitive values are Key Vault references: `@Microsoft.KeyVault(SecretUri=...)`.
- Each slot has its own system-assigned Managed Identity, granted **Key Vault Secrets User**.
- Slot-specific values (such as `SLOT_LABEL`) are marked as deployment slot settings so they stay with the slot during a swap.

### MilestoneFunction

Runs on `0 */5 * * * *`. For each habit it loads check-ins, computes the current streak, and asks `MilestoneChecker.GetCrossedMilestone(lastCheckedStreak, currentStreak)`. Only when a milestone is crossed does it look up the user's email. It then persists `LastCheckedStreak`, which makes the function **idempotent**: re-running it never re-announces the same milestone.

### CI/CD pipeline

```
push / PR to main
      |
 build-and-test  (restore, build, xUnit tests)      <- failing tests stop everything
      |
 changes         (path filter: what changed?)
      |
      +--> deploy-userservice
      |       deploy to staging --> smoke test /health (must report this commit SHA)
      |       --> swap staging <-> production --> verify production --> rollback swap on failure
      |
      +--> deploy-milestonefunction
```

- **Deploys are switched off:** the Azure resources were torn down after verification, so the deploy jobs only run when the repository variable `AZURE_DEPLOY_ENABLED` is `true`. Build and tests always run.
- **Tests gate deploys:** deployment jobs `need` the test job and only run on a push to `main`.
- **Passwordless:** GitHub authenticates to Azure with OIDC federation (federated credential on the `main` branch, Contributor on one resource group). No client secret is stored.
- **Build once:** the published output is uploaded as an artifact and deployed, not rebuilt.
- **Path filters** (`dorny/paths-filter`):

  | Changed path | Deploys |
  |---|---|
  | `UserService/**` | UserService |
  | `MilestoneFunction/**`, `HabitService/**`, `UserService/**` | MilestoneFunction (it references both) |
  | `.github/workflows/**` | Everything |

- **Concurrency:** one deploy per service at a time.
- **Version stamping:** the commit SHA is baked into the assembly (`SourceRevisionId`) and exposed by `/health`, so the pipeline can prove which build is running.

### Zero-downtime release flow

1. Deploy the new build to the **staging** slot.
2. Smoke test staging `/health`, requiring the exact commit SHA.
3. **Swap** staging and production. The new version is already warm, so users see no cold start.
4. Verify production `/health` returns the same SHA.
5. If verification fails, swap back. The previous version is still in the other slot.

### Problems solved along the way

| Problem | Cause | Fix |
|---|---|---|
| App served a PHP container | `CURRENT_STACK` metadata was "Unknown" | Set Stack to .NET 10 in Portal general settings |
| Crash loop, exit code 150 | .NET 10 app on a .NET 8 runtime | `--linux-fx-version "DOTNETCORE:10.0"` |
| Function deployed, zero functions listed | Hidden `.azurefunctions` folder dropped from artifact | `include-hidden-files: true` on upload |
| Staging smoke test crashed (NullReference) | Git-ignored `appsettings.json` never reached CI | Supply `Jwt__*` App Settings and Key Vault `JwtKey` on both slots |
| Key Vault "not allowed" for its own creator | RBAC mode needs explicit roles | Secrets Officer for the admin, Secrets User for identities |
| SQL error 40615 | Client IP not in firewall | Add client IPv4 firewall rule |
| Free SQL DB paused | Monthly free vCore-second allowance used | Left paused; avoided upgrading to stay free |
| Connection string saved under wrong name | CLI quoting | Delete and re-add via Portal |

## Running with Docker

The quickest way to run the whole system. One command starts SQL Server and the three services.

**Requirements:** Docker Desktop (on Windows it uses WSL 2) with enough memory for SQL Server, about 2 GB.

```bash
# 1. Create your local settings file from the template
cp .env.example .env          # Windows Command Prompt: copy .env.example .env

# 2. Edit .env and set SA_PASSWORD, JWT_KEY and INTERNAL_API_KEY

# 3. Build and start everything
docker compose up --build
```

`.env` is git-ignored, so your secrets are never committed. `.env.example` only holds placeholders.

| Setting in `.env` | Purpose |
|---|---|
| `SA_PASSWORD` | Password for the SQL Server container's `sa` login (8+ characters with upper case, lower case, a digit and a symbol; avoid `;`) |
| `JWT_KEY` | JWT signing key shared by all three services (at least 32 characters) |
| `INTERNAL_API_KEY` | Shared secret for service-to-service calls (`X-Internal-Api-Key`) |

| What | Where |
|---|---|
| UserService | http://localhost:5139 |
| HabitService | http://localhost:5096 |
| NotificationService | http://localhost:5087 |
| API docs (Scalar) | `/scalar/v1` on each service, for example http://localhost:5139/scalar/v1 |
| SQL Server | `localhost,1433`, login `sa`, password from `.env` (check the `ports` line of `sqlserver` in `docker-compose.yml`) |

**Try it:** open the UserService Scalar page, register a user and log in to get a JWT. Then open the HabitService Scalar page, authorize with the token, create a habit and check in.

**Stop it:** `docker compose down` keeps the data in a Docker volume. `docker compose down -v` also deletes the data.

### How it works

- **Startup order:** SQL Server starts first and the services wait for its health check, because SQL Server needs 20 to 30 seconds before it accepts connections.
- **Databases:** each service creates and migrates its own database at startup when `MigrateOnStartup=true`, which Compose sets. Normal runs outside Docker are unaffected, because the flag isn't set there.
- **Configuration:** everything comes from environment variables in `docker-compose.yml` and `.env`. No `appsettings.json` is baked into an image, and the `.dockerignore` files keep local config out.
- **Networking:** the services reach each other by Compose service name (`http://notificationservice:8080/`), not `localhost`. Each container listens on port 8080, and Compose maps that to the host ports above.
- **Images:** multi-stage builds (SDK to build, small ASP.NET runtime image to run), and the app runs as a non-root user.
- **Data:** SQL Server data lives in the named volume `sqldata`, so it survives restarts.
- **Scalar docs:** Compose sets `ASPNETCORE_ENVIRONMENT=Development` so the API docs are available. Remove it for a production-style run.

### Using your own SQL Server instead of the container

Optional. Add these to your own `.env` to point the services at a SQL Server on your machine:

```
DB_SERVER=host.docker.internal,1433
DB_USER=your_sql_login
DB_PASSWORD=your_sql_login_password
USER_DB=your_user_database
HABIT_DB=your_habit_database
NOTIFICATION_DB=your_notification_database
```

Without these lines the defaults apply: the `sqlserver` container, the `sa` login and the `HabitTrack_*` database names. Your SQL Server needs TCP/IP enabled on port 1433, SQL authentication, a SQL login with access to the databases, and an open firewall port. The container still starts in this mode, so give the `sqlserver` service a different host port in `docker-compose.yml` (for example `"1434:1433"`) if your local instance already uses 1433.

### Not included

`MilestoneFunction` is not part of the Compose setup, because it needs the Azure Functions tooling and a storage emulator. On Apple Silicon, SQL Server runs under emulation, so the first start is slow.

## Running locally

1. In each service folder, copy `appsettings.example.json` to `appsettings.json` (git-ignored) and fill in your values. The `Jwt` settings must match in all three services, and `InternalApiKey` must match in HabitService and NotificationService. For `MilestoneFunction`, copy `local.settings.example.json` to `local.settings.json`.
2. Apply migrations in each service: `Update-Database` (Package Manager Console) or `dotnet ef database update`.
3. Optional: set `Anthropic:ApiKey` for HabitService to enable the insights endpoint. Without it the endpoint returns the fallback message.
4. Start the services together (multiple startup projects in Visual Studio).
5. Browse API docs at `/scalar/v1` on each service.
6. Run the tests: `dotnet test HabitTrack.slnx`

## Design decisions and tradeoffs

| Decision | Why | What it costs | At larger scale |
|---|---|---|---|
| **Synchronous, best-effort HTTP from HabitService to NotificationService** | Simple and easy to debug. A failed notification is caught and logged, so it never breaks the check-in that already succeeded. | The call is awaited inside the request, which adds latency. There is no retry, so a notification sent while NotificationService is down is lost. | Publish a `MilestoneReached` event to a queue (for example Azure Service Bus) with an outbox table, so delivery is retried and the services are decoupled. |
| **Database per service** | Services deploy and change independently, with no shared schema. | No cross-service joins or transactions. `MilestoneFunction` reads both databases directly as a shortcut. | Have the Function call service APIs, or consume events, instead of reading other services' databases. |
| **Milestone detection in two places** (inline on check-in, and a timer function) | The inline path is immediate. The timer function is a safety net that catches anything missed, and it is idempotent through `LastCheckedStreak`. | Two code paths to keep consistent. | Pick one source of truth, ideally event-driven, and keep the timer only for reconciliation. |
| **Shared symmetric JWT key** | Every service validates tokens locally, with no call to UserService. | Any service holding the key could also issue tokens, and rotating it means touching every service. | Asymmetric signing (RS256): only UserService holds the private key, and the others verify with a public key. |
| **In-memory caches** (streaks, insights) | Fast and needs no extra infrastructure. | Per instance, lost on restart, and not shared across scaled-out instances. | A distributed cache such as Redis. |
| **Fixed polling interval for at-risk checks** (NotificationService background job, every minute) | Simple, and works on any host. | Does work even when nothing changed, and every instance runs it. | A scheduled job or event-driven trigger, plus a lock so only one instance runs it. |

## Known simplifications

- In-memory caches (streaks and insights) rather than a distributed cache; they are per instance and reset on restart
- Insight cache is keyed by habit only, so a new check-in does not invalidate it until the 12 hours expire
- Synchronous HTTP between services instead of a message queue
- At-risk hour is a fixed UTC value, not per-user time zone
- Some shared constants are duplicated across services
- The Function reads the databases directly rather than calling service APIs
- `/health` does not check database connectivity
- Only UserService and the Function were deployed to Azure
- The Function is not containerized, so Docker Compose runs the three services only
- Compose runs the services in the Development environment so the API docs are available, which is not a production configuration
